# pH SvelteKit 3 + ReScript Rewrite

**Date:** 2026-09-06
**Status:** Complete
**Branch:** `v2`
**Compatibility baseline:** tag `v1` (`1bdab5d`)

## One sentence

Rewrite pH from scratch as a small SvelteKit 3 application in which Svelte owns reactive presentation, ReScript owns typed application logic, and narrow JavaScript adapters preserve the v1 password algorithm.

## Completion proof

The rewrite is complete when legacy hash fixtures remain stable, site addresses resolve to a documented password realm, application failures cross typed boundaries, confirmation cannot become stale, clipboard failures are testable without a browser, and checks, tests, and the production build pass.

Correctness takes priority over maximizing the amount of ReScript or demonstrating a language feature. Use a feature only where it makes the application safer or clearer.

## Implementation status

Phases 1 and 2 are complete. ReScript 12 compiles in-source ESM and genType bindings before development, checks, tests, and production builds. The `LetUnwrap` experimental feature is enabled so `generatePassword` can use `let?` for typed result propagation. Svelte imports that generated API as the current bridge proof.

The copied MD5 and password-constraint sources live under `src/lib/pwdhash/legacy`; narrow ESM changes connect them through a primitive-string adapter. The typed realm resolver uses a pinned ICANN Public Suffix List plus the explicit `org.ru` compound-suffix rule and returns `MissingAddress` or `InvalidAddress` instead of exposing parser failures. Tests cover realm policy, typed failures, two legacy hash fixtures, and the intentional literal treatment of `@@`.

The copied algorithm files are excluded from Prettier and ESLint so their layout remains directly comparable with tag `v1`. Project-owned adapters remain checked. `@rescript/runtime` is a direct dependency because the generated application modules use runtime helpers such as `Option.flatMap`.

Phases 3, 4, and 5 are complete. The application has typed form, confirmation, and clipboard boundaries, Node tests for each, and the finished Svelte form with immediate generation and explicit copy feedback. Checks, tests, the production build, GitHub Actions deployment, and the production smoke test pass.

## Scope

In scope:

- Rebuild the current single-page UI with Svelte 5 runes.
- Preserve the v1 password-generation algorithm once a password realm has been selected.
- Convert unsafe domain-extraction failures into typed results.
- Model password confirmation with a ReScript variant.
- Use an explicit Copy action with typed success and failure handling.
- Keep core application logic testable in Node.
- Preserve applicable third-party license notices.

Out of scope:

- Porting the MD5/HMAC primitive or legacy password-constraint algorithm to ReScript.
- Preserving the obsolete `@@` source-password prefix behavior.
- Restoring the unused advanced mode, global password, or constraint controls found in older upstream code.
- Automatically copying after every password keystroke.
- Adding a backend, persistence, or experimental SvelteKit features.
- Building a comprehensive browser-test suite or chasing a coverage target.

The removed `@@` behavior is an intentional compatibility exception. Inputs beginning with `@@` are treated literally in v2: they are not detected or stripped before hashing. The legacy hash implementation nevertheless retains its fixed two-character output-length offset, formerly expressed as `SPH_kPasswordPrefix.length`, because changing it would alter every generated password. That constant is an algorithm parameter, not a prefix feature.

## Current and target shape

V1 is available from the `v1` tag as the hash-algorithm compatibility source. Realm selection intentionally follows the v2 policy below.

V1 couples password generation, clipboard access, and presentation to DOM globals:

```text
DOM events
  -> Generate() reads form fields
    -> domain extractor
    -> hashed-password object
    -> document.execCommand("copy")
    -> direct style mutation
```

V2 separates those responsibilities:

```text
Svelte UI and reactivity
  -> generated ReScript application API
    -> explicit legacy JavaScript adapters
      -> unchanged v1 algorithms

Svelte copy action
  -> ReScript result mapping
    -> injected browser clipboard adapter
```

## ReScript build contract

Follow ReScript 12 conventions for configuration, in-source ESM output, module layout, and genType-generated TypeScript bindings.

Required properties:

- ReScript sources live under `src/lib` in a clearly named domain or application directory.
- Generated `.res.js` and `.gen.tsx` files are ignored by Git.
- `gentypeconfig` uses ESM and the same `bundler` module resolution as TypeScript.
- TypeScript has `allowJs` enabled, as required by genType.
- genType bindings are generated only for the public Svelte-facing API.
- Svelte imports only that public generated API, preferably through `#lib`.
- Low-level legacy bindings are not public to Svelte components.
- `dev`, `build`, `check`, and test workflows compile ReScript before consuming generated output.
- Development watch mode keeps ReScript output current while Vite runs.
- Tests can import compiled ReScript modules directly and run in Vitest's Node environment.
- ReScript's `LetUnwrap` experimental feature is enabled for `let?` result propagation. Revisit this flag when ReScript stabilizes or replaces the syntax.

The exact generated paths and scripts should follow the installed ReScript version rather than being invented in this spec. Document any non-obvious command in `package.json` or the project README.

## Ownership boundaries

### Svelte owns

- `$state` and `$derived`
- Form bindings and DOM events
- Masking or revealing the generated password
- Transient copy state such as idle, copied, or failed
- The concrete browser clipboard implementation

### ReScript owns

- Password-generation orchestration
- Site-address normalization and supported registrable-realm selection
- Form validation and presentation data
- Confirmation-state calculation and presentation data
- Mapping clipboard promise rejection to a typed result
- Exhaustive handling of application states

Prefer pure ReScript functions. Browser effects must enter through narrow injected functions.

### Legacy JavaScript owns

- `SPH_HashedPassword`
- Required MD5/HMAC primitives
- The legacy password-constraint algorithm

Do not duplicate or refactor those hash algorithms during the rewrite.

## Legacy source strategy

Copy only the hash files required by the target application from tag `v1`, preferably from `src/lib`:

- `hashed-password.js`
- `md5.js`

Do not copy jQuery, the autocomplete plugin, `domain-extractor.js`, `pwdhash.js`, or other DOM-driven orchestration unless implementation evidence shows that a required algorithm depends on them.

Keep copied files recognizable and easy to compare with v1. Preserve their copyright and license headers. If a file must be changed for ESM interoperability, limit the change to exports or a short modification note.

Exclude the copied `md5.js` and `hashed-password.js` files from automatic formatting and lint rewrites. Do not exclude the project-owned adapter that wraps them.

The ESM bridge must explicitly connect `md5.js` to `hashed-password.js`, which calls `b64_hmac_md5`. Do not rely on browser globals being shared across separate modules. Prefer the smallest explicit exports and imports that preserve the legacy implementation. `hashed-password.js` also uses `SPH_kPasswordPrefix.length` only as a fixed output-length offset. Give the ESM-local legacy implementation an explicit constant with the value `"@@"`; do not copy the `Generate()` prefix detection or stripping from `pwdhash.js`.

The legacy hashed-password constructor returns an object whose `toString()` yields the password. Do not bind that constructor as if it returned a primitive string. Use a small explicit JavaScript adapter:

```js
export function generateLegacyPassword(password, domain) {
	return String(new SPH_HashedPassword(password, domain));
}
```

The exact export arrangement may differ, but the adapter must return a primitive string and contain no password-generation logic of its own.

### Password realm resolution

`Realm.res` resolves a site address to its registrable domain through the pinned `tldts-icann` dependency. It treats `org.ru` as a compound suffix, matching the application's established realm policy even though that rule is absent from the dependency's ICANN-only data. It accepts a hostname, a complete web address, or a protocol-relative address; trims surrounding whitespace; and returns the same realm for subdomains. Private suffixes are deliberately excluded, so `foo.blogspot.com` resolves to `blogspot.com`.

Realm selection is intentionally not v1-compatible. It rejects malformed text, IP addresses, bare public suffixes, and the reserved `.invalid` suffix. Empty input returns `MissingAddress`; other rejected input returns `InvalidAddress`. The exact pinned dependency version is part of the password algorithm and must change only through a reviewed update.

## Password generation

### Public behavior

Password generation has exactly two inputs:

- `domainInput`
- `password`

There is no options model. The old advanced-mode concepts and the `@@` prefix behavior are not part of v2.

Expose an API approximately equivalent to:

```rescript
type generationError =
  | MissingAddress
  | InvalidAddress

let generatePassword: (
  ~domainInput: string,
  ~password: string,
) => result<string, generationError>
```

The exact generated TypeScript signature may differ, but its possible outcomes must remain explicit.

### Domain extraction

Resolve the realm before hashing. The resolver is a pure calculation over the supplied address and returns typed failures:

```rescript
let resolve = input =>
  switch getDomain(normalizeProtocolRelativeAddress(input)) {
  | Some(realm) => Ok(realm)
  | None => Error(InvalidAddress)
  }
```

`MissingAddress` means the trimmed input is empty. `InvalidAddress` means the input has no valid supported registrable domain.

Use `let?` to stop generation before hashing when domain extraction fails:

```rescript
let generatePassword = (~domainInput, ~password) => {
  let? realm = resolve(domainInput)
  Ok(generateLegacyPassword(password, realm))
}
```

### Reactive UI behavior

Svelte calls generation synchronously whenever either the domain or source password changes. Generation is inexpensive enough that delaying presentation adds latency without a meaningful reduction in work.

Address validation remains neutral until generation is meaningfully requested. A request occurs when either:

- the source password is non-empty, or
- the user activates Copy.

Once requested, a failed realm resolution marks the address field and provides an accessible error message. Editing the address or source password recalculates the form presentation immediately and clears the error when generation succeeds.

Confirmation input does not trigger generation or domain validation. It only recalculates confirmation state.

### Bookmarklet and focus behavior

The footer exposes a `pH` bookmarklet. It opens the current application URL with the source page URL encoded in the fragment. On mount, the application decodes that fragment, accepts the raw v1 fragment form as well, and passes its value through the typed domain extractor before placing the extracted domain in the Domain field.

Initial focus follows the available context: focus Domain for a normal load, or Password when the bookmarklet supplied a domain. The document title and visible heading are `PwdHash Generator`.

The generated-password field is labeled `Generated Password`. It stays masked outside focus; on focus it reveals and selects the complete value so a user can manually copy it when browser clipboard access fails.

## Confirmation

Represent confirmation as a pure ReScript variant:

```rescript
type confirmationState =
  | Empty
  | MatchingPrefix
  | ExactMatch
  | Mismatch
```

Calculate it from current inputs only:

```rescript
let getConfirmationState = (~password, ~confirmation) =>
  if confirmation == "" {
    Empty
  } else if confirmation == password {
    ExactMatch
  } else if password->String.startsWith(confirmation) {
    MatchingPrefix
  } else {
    Mismatch
  }
```

Expected presentation:

| State            | Meaning                               | Presentation |
| ---------------- | ------------------------------------- | ------------ |
| `Empty`          | No confirmation entered               | Neutral      |
| `MatchingPrefix` | Entered text matches a shorter prefix | Yellow       |
| `ExactMatch`     | Complete match                        | Green        |
| `Mismatch`       | Values diverge                        | Red or pink  |

Convert the variant to a small UI-friendly value through an exhaustive ReScript match. Do not use a wildcard branch in the match intended to demonstrate exhaustiveness. Svelte owns the actual CSS colors.

Svelte derives confirmation from the current source password and confirmation input:

```text
source password ------+-> confirmation state -> UI
confirmation input ---+
```

This preserves v1 behavior: confirmation verifies that the user repeated the source password correctly. Editing the source password after an exact match must immediately remove the green state. Domain changes do not affect confirmation.

## Clipboard

### Product decision

V2 uses an explicit Copy action. It does not automatically write to the clipboard after every password keystroke.

The web Clipboard API has no portable way to mark a copied item as sensitive or exclude it from clipboard history. Explicit copy avoids spamming clipboard managers, provides a reliable user activation, and gives the user control over when the generated password leaves the application.

Activating Copy is also a generation-validation trigger. If generation currently fails, do not call the clipboard and show the domain error. If generation succeeds, copy the current generated password.

Copy is the form submission action, so pressing Enter in any form field follows the same validation and explicit-copy path as activating the Copy button.

### Typed boundary

Inject the browser write operation into ReScript:

```rescript
type copyError =
  | CopyFailed

type writeText = string => promise<unit>

let copyToClipboard: (writeText, string) => promise<result<unit, copyError>> =
  async (writeText, text): result<unit, copyError> => {
    try {
      await writeText(text)
      Ok()
    } catch {
    | _ => Error(CopyFailed)
    }
  }
```

Exact ReScript syntax should match version 12. The important contract is that the asynchronous public result is `promise<result<unit, copyError>>`, not a synchronous `result`.

The production adapter calls `navigator.clipboard.writeText`. Svelte maps the result to transient idle, copied, or failed presentation. Do not invent more detailed errors unless browsers expose a reliable distinction that improves the UI.

## Public ReScript API

Keep the Svelte-facing surface approximately this small:

```text
generatePassword(...)
resolve(...)
presentForm(...)
presentConfirmation(...)
copyToClipboard(...)
copyFeedbackMessage(...)
```

Svelte must not know about legacy constructors, parser internals, or ReScript compiler representations that can instead be converted to stable UI-friendly values.

## Testing

Use Vitest and keep the initial suite small. Most tests run in Node without a browser.

### Characterization fixtures

Before changing orchestration, capture a small number of known v1 outputs with:

```text
domain input
source password
expected generated password
```

Also capture a compact realm-resolution corpus with input and expected realm or typed failure. Include normalization, compound suffixes, and subdomain sharing, but do not build a large matrix. Because `@@` handling is intentionally removed, do not require compatibility for source passwords beginning with `@@`.

### Required tests

- One or two v1 password-compatibility fixtures.
- Representative site addresses resolve to the expected registrable realm, including compound suffixes, the explicit `org.ru` rule, and protocol-relative input.
- Different subdomains produce the same realm and generated password.
- Empty input returns `Error(MissingAddress)`; malformed, reserved, and IP-address input returns `Error(InvalidAddress)`.
- Confirmation produces `Empty`, `MatchingPrefix`, `ExactMatch`, and `Mismatch` for representative values.
- Changing the source password after `ExactMatch` produces the appropriate non-match state.
- An injected resolving clipboard writer produces `Ok()`.
- An injected rejecting clipboard writer produces `Error(CopyFailed)`.
- Clipboard writing is not invoked when generation fails.

Do not test generated declarations, compiler exhaustiveness itself, trivial forwarding wrappers, SvelteKit internals, or a real system clipboard in Node.

Add further tests when a real bug, compatibility regression, or discovered edge case justifies them. Browser tests remain optional until behavior cannot be adequately protected below that level.

## Deployment

Deploy pH as a fully prerendered static SvelteKit site using `@sveltejs/adapter-static`. The static adapter writes the deployable site to ignored `build/`; generated production files are never committed.

GitHub Actions runs `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm test`, and `pnpm build` for pull requests and pushes to `v2` and `main`. Only `main` may upload the generated `build/` artifact and deploy it to GitHub Pages. Manual workflow runs are also restricted to `main` for deployment.

Production is served at `https://ph.leftium.com/`, so the SvelteKit base path remains empty. Do not configure `/pH`, create a `gh-pages` branch, or add an SPA fallback. The root route is prerendered as HTML and hydrates in the browser.

The old `main/docs` publishing model is retired. `docs/` held generated v1 production files, including its historical `CNAME`, and is not part of the new source tree. The GitHub Pages repository setting is authoritative for the existing `ph.leftium.com` custom domain; change its publishing source to GitHub Actions, retain HTTPS enforcement, and leave DNS unchanged unless verification identifies a real issue.

The existing `v1` tag points to the known-good production revision. If the new deployment has a serious issue, revert the `v2` merge on `main` to restore the committed v1 `docs/` site, then temporarily change the Pages publishing source back to `main/docs`. No user password material may leave the browser through the static deployment.

The GitHub Actions deployment has been completed and the production smoke test passed at `https://ph.leftium.com/`. The deployed site loads over HTTPS, serves root-relative assets, preserves password generation behavior, reports typed domain errors, shows confirmation states correctly, invalidates stale confirmation, and copies successfully without sending password material to a server.

Keep the application portable as static assets. A later move to Cloudflare Pages should not require application architecture changes. Cloudflare Workers is not part of this rewrite unless a Worker-specific requirement emerges.
