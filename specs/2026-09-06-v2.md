# pH SvelteKit 3 + ReScript Rewrite

**Date:** 2026-09-06
**Status:** Draft
**Branch:** `v2`
**Compatibility baseline:** tag `v1` (`1bdab5d`)

## One sentence

Rewrite pH from scratch as a small SvelteKit 3 application in which Svelte owns reactive presentation, ReScript owns typed application logic, and narrow JavaScript adapters preserve the v1 password algorithm.

## Completion proof

The rewrite is complete when characterization fixtures match v1 for supported inputs, application failures cross typed boundaries, confirmation cannot become stale, clipboard failures are testable without a browser, and checks, tests, and the production build pass.

Correctness takes priority over maximizing the amount of ReScript or demonstrating a language feature. Use a feature only where it makes the application safer or clearer.

## Scope

In scope:

- Rebuild the current single-page UI with Svelte 5 runes.
- Preserve the v1 password-generation algorithm for ordinary inputs.
- Convert unsafe domain-extraction failures into typed results.
- Model password confirmation with a ReScript variant.
- Use an explicit Copy action with typed success and failure handling.
- Keep core application logic testable in Node.
- Preserve applicable third-party license notices.

Out of scope:

- Porting the MD5/HMAC primitive or legacy password-constraint algorithm to ReScript.
- Preserving the obsolete `@@` source-password prefix behavior.
- Restoring the unused advanced mode, global password, or constraint controls found in older upstream code.
- Automatically copying after every password keystroke.
- Adding a backend, persistence, or experimental SvelteKit features.
- Building a comprehensive browser-test suite or chasing a coverage target.

The removed `@@` behavior is an intentional compatibility exception. Inputs beginning with `@@` are treated literally in v2: they are not detected or stripped before hashing. The legacy hash implementation nevertheless retains its fixed two-character output-length offset, formerly expressed as `SPH_kPasswordPrefix.length`, because changing it would alter every generated password. That constant is an algorithm parameter, not a prefix feature.

## Current and target shape

V1 is available from the `v1` tag, which is the authoritative compatibility source.

V1 couples password generation, clipboard access, and presentation to DOM globals:

```text
DOM events
  -> Generate() reads form fields
    -> domain extractor
    -> hashed-password object
    -> document.execCommand("copy")
    -> direct style mutation
```

V2 separates those responsibilities:

```text
Svelte UI and reactivity
  -> generated ReScript application API
    -> explicit legacy JavaScript adapters
      -> unchanged v1 algorithms

Svelte copy action
  -> ReScript result mapping
    -> injected browser clipboard adapter
```

## ReScript build contract

Follow ReScript 12 conventions for configuration, in-source ESM output, module layout, and genType-generated TypeScript bindings.

Required properties:

- ReScript sources live under `src/lib` in a clearly named domain or application directory.
- Generated `.res.js` and `.gen.tsx` files are ignored by Git.
- `gentypeconfig` uses ESM and the same `bundler` module resolution as TypeScript.
- TypeScript has `allowJs` enabled, as required by genType.
- genType bindings are generated only for the public Svelte-facing API.
- Svelte imports only that public generated API, preferably through `#lib`.
- Low-level legacy bindings are not public to Svelte components.
- `dev`, `build`, `check`, and test workflows compile ReScript before consuming generated output.
- Development watch mode keeps ReScript output current while Vite runs.
- Tests can import compiled ReScript modules directly and run in Vitest's Node environment.

The exact generated paths and scripts should follow the installed ReScript version rather than being invented in this spec. Document any non-obvious command in `package.json` or the project README.

## Ownership boundaries

### Svelte owns

- `$state` and `$derived`
- Form bindings and DOM events
- Debouncing generation input
- Field classes, colors, and messages
- Masking or revealing the generated password
- Transient copy state such as idle, copied, or failed
- The concrete browser clipboard implementation

### ReScript owns

- Password-generation orchestration
- A compatibility port of domain extraction and its typed results
- Confirmation-state calculation
- Mapping clipboard promise rejection to a typed result
- Exhaustive handling of application states

Prefer pure ReScript functions. Browser effects must enter through narrow injected functions.

### Legacy JavaScript owns

- `SPH_HashedPassword`
- Required MD5/HMAC primitives
- The legacy password-constraint algorithm

Do not duplicate or refactor those hash algorithms during the rewrite.

## Legacy source strategy

Copy only the hash files required by the target application from tag `v1`, preferably from `src/lib`:

- `hashed-password.js`
- `md5.js`

Do not copy jQuery, the autocomplete plugin, `domain-extractor.js`, `pwdhash.js`, or other DOM-driven orchestration unless implementation evidence shows that a required algorithm depends on them.

Keep copied files recognizable and easy to compare with v1. Preserve their copyright and license headers. If a file must be changed for ESM interoperability, limit the change to exports or a short modification note.

The ESM bridge must explicitly connect `md5.js` to `hashed-password.js`, which calls `b64_hmac_md5`. Do not rely on browser globals being shared across separate modules. Prefer the smallest explicit exports and imports that preserve the legacy implementation. `hashed-password.js` also uses `SPH_kPasswordPrefix.length` only as a fixed output-length offset. Give the ESM-local legacy implementation an explicit constant with the value `"@@"`; do not copy the `Generate()` prefix detection or stripping from `pwdhash.js`.

The legacy hashed-password constructor returns an object whose `toString()` yields the password. Do not bind that constructor as if it returned a primitive string. Use a small explicit JavaScript adapter:

```js
export function generateLegacyPassword(password, domain) {
  return String(new SPH_HashedPassword(password, domain));
}
```

The exact export arrangement may differ, but the adapter must return a primitive string and contain no password-generation logic of its own.

### Domain extractor port

Port `domain-extractor.js` as a behavioral compatibility port to ReScript rather than replacing it with a current Public Suffix List library. Its historic suffix table and string-processing quirks are part of the effective password algorithm because the extracted result is hashed. Retain its attribution and license notice in the ReScript source.

The port must preserve the legacy behavior for compatible inputs, including first-occurrence protocol replacement, non-validation of hostnames, casing, and the historic suffix table. It must not use `tldts`, `psl`, `URL`, or another general parser in the generation path. Characterization fixtures from `v1` are the oracle.

The port may improve the failure boundary: an empty or otherwise unmatchable input must produce a typed result rather than the legacy unchecked match-index exception.

## Password generation

### Public behavior

Password generation has exactly two inputs:

- `domainInput`
- `password`

There is no options model. The old advanced-mode concepts and the `@@` prefix behavior are not part of v2.

Expose an API approximately equivalent to:

```rescript
type generationError =
  | MissingDomain
  | DomainExtractionFailed

let generatePassword: (
  ~domainInput: string,
  ~password: string,
) => result<string, generationError>
```

The exact generated TypeScript signature may differ, but its possible outcomes must remain explicit.

### Domain extraction

The v1 extractor throws for an empty or otherwise unmatchable input because it indexes a failed regular-expression match. Convert that unsafe behavior at the ReScript boundary:

```rescript
let extractDomain = input =>
  if input->String.trim == "" {
    Error(MissingDomain)
  } else {
    switch extractDomainCompat(input) {
    | Ok(domain) => Ok(domain)
    | Error(_) => Error(DomainExtractionFailed)
    }
  }
```

Do not add `InvalidDomain` or speculative validation. `MissingDomain` means the trimmed input is empty; `DomainExtractionFailed` means the legacy extractor failed for a non-empty input.

Use `let?` to stop generation before hashing when domain extraction fails:

```rescript
let generatePassword = (~domainInput, ~password) => {
  let? domain = extractDomain(domainInput)
  Ok(generateLegacyPassword(password, domain))
}
```

### Reactive UI behavior

Svelte calls generation when either the domain or source password changes, after an approximately 200 ms debounce.

The debounce is presentation policy, not part of ReScript domain logic or password compatibility. It should prevent obsolete pending work from overwriting newer state.

Domain validation remains neutral until generation is meaningfully requested. A request occurs when either:

- the source password is non-empty, or
- the user activates Copy.

Once requested, a failed generation result marks the domain field and provides an accessible error message. Editing the domain or source password reruns generation after the debounce and clears the error when generation succeeds.

Confirmation input does not trigger generation or domain validation. It only recalculates confirmation state.

## Confirmation

Represent confirmation as a pure ReScript variant:

```rescript
type confirmationState =
  | Empty
  | MatchingPrefix
  | ExactMatch
  | Mismatch
```

Calculate it from current inputs only:

```rescript
let getConfirmationState = (~password, ~confirmation) =>
  if confirmation == "" {
    Empty
  } else if confirmation == password {
    ExactMatch
  } else if password->String.startsWith(confirmation) {
    MatchingPrefix
  } else {
    Mismatch
  }
```

Expected presentation:

| State | Meaning | Presentation |
| --- | --- | --- |
| `Empty` | No confirmation entered | Neutral |
| `MatchingPrefix` | Entered text matches a shorter prefix | Yellow |
| `ExactMatch` | Complete match | Green |
| `Mismatch` | Values diverge | Red or pink |

Convert the variant to a small UI-friendly value through an exhaustive ReScript match. Do not use a wildcard branch in the match intended to demonstrate exhaustiveness. Svelte owns the actual CSS colors.

Svelte derives confirmation from both the current generated password and confirmation input:

```text
domain ---------+
                 +-> generated password --+
source password +                         +-> confirmation state -> UI
confirmation input -----------------------+
```

This fixes v1's stale-confirmation bug: changing the domain or source password after an exact match must immediately remove the green state once the generated password changes.

## Clipboard

### Product decision

V2 uses an explicit Copy action. It does not automatically write to the clipboard after every password keystroke.

The web Clipboard API has no portable way to mark a copied item as sensitive or exclude it from clipboard history. Explicit copy avoids spamming clipboard managers, provides a reliable user activation, and gives the user control over when the generated password leaves the application.

Activating Copy is also a generation-validation trigger. If generation currently fails, do not call the clipboard and show the domain error. If generation succeeds, copy the current generated password.

### Typed boundary

Inject the browser write operation into ReScript:

```rescript
type copyError =
  | CopyFailed

type writeText = string => promise<unit>

let copyToClipboard: (writeText, string) => promise<result<unit, copyError>> =
  async (writeText, text): result<unit, copyError> => {
    try {
      await writeText(text)
      Ok()
    } catch {
    | _ => Error(CopyFailed)
    }
  }
```

Exact ReScript syntax should match version 12. The important contract is that the asynchronous public result is `promise<result<unit, copyError>>`, not a synchronous `result`.

The production adapter calls `navigator.clipboard.writeText`. Svelte maps the result to transient idle, copied, or failed presentation. Do not invent more detailed errors unless browsers expose a reliable distinction that improves the UI.

## Public ReScript API

Keep the Svelte-facing surface approximately this small:

```text
generatePassword(...)
getConfirmationState(...)
confirmationClass(...)
copyToClipboard(...)
```

Svelte must not know about legacy constructors, legacy exceptions, or ReScript compiler representations that can instead be converted to stable UI-friendly values.

## Testing

Use Vitest and keep the initial suite small. Most tests run in Node without a browser.

### Characterization fixtures

Before changing orchestration, capture a small number of known v1 outputs with:

```text
domain input
source password
expected generated password
```

Also capture a compact domain-extraction corpus with input and expected extracted domain (or legacy failure). Include representative normalization and suffix-table cases, but do not build a large matrix. Because `@@` handling is intentionally removed, do not require compatibility for source passwords beginning with `@@`.

### Required tests

- One or two v1 password-compatibility fixtures.
- Representative domain-extraction fixtures match v1 for successful inputs; non-empty legacy failures become `Error(DomainExtractionFailed)`.
- Empty domain with a non-empty password returns `Error(MissingDomain)`.
- Non-empty input rejected by the legacy extractor returns `Error(DomainExtractionFailed)`.
- Confirmation produces `Empty`, `MatchingPrefix`, `ExactMatch`, and `Mismatch` for representative values.
- Changing the generated password after `ExactMatch` produces the appropriate non-match state.
- An injected resolving clipboard writer produces `Ok()`.
- An injected rejecting clipboard writer produces `Error(CopyFailed)`.
- Clipboard writing is not invoked when generation fails.

Do not test generated declarations, compiler exhaustiveness itself, trivial forwarding wrappers, SvelteKit internals, or a real system clipboard in Node.

Add further tests when a real bug, compatibility regression, or discovered edge case justifies them. Browser tests remain optional until behavior cannot be adequately protected below that level.

## Deployment

Use `adapter-static` and deploy the static output to GitHub Pages, preserving the v1 deployment model. Configure the repository base path, fallback, and Pages workflow as required by the actual repository URL.

Keep the application portable as static assets. A later move to Cloudflare Pages should not require application architecture changes. Cloudflare Workers is not part of this rewrite unless a Worker-specific requirement emerges.
